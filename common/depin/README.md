# DePIN Tokenomics — `$TRI` On-Chip Token Accumulator

<!-- SPDX-License-Identifier: Apache-2.0 -->
<!-- DOI: 10.5281/zenodo.19227877 -->

## Overview

This directory contains the canonical hardware implementation of the **$TRI token accumulator** — the on-chip proof-of-compute counter that enables NeuronConstant Trinity chips to participate in a Decentralised Physical Infrastructure Network (DePIN) settlement layer.

Each chip accumulates `$TRI` tokens in hardware as it completes attestable compute jobs. An off-chip prover reads the accumulated balance and mints ERC-20 `$TRI` tokens 1:1 on the settlement layer.

---

## How It Works

### 1. Chip Emits `attest_pulse` on Valid Job

The attestation trigger is a single-cycle pulse (`attest_pulse`) generated by the tile's top-level logic when a verifiable compute job completes:

| Chip | `attest_pulse` Source | `reward_amount` |
|---|---|---|
| **Phi** | `phi_post_done` — after Lucas POST validates the phi anchor | `1` |
| **Euler** | `multi_rcpt_ok` — from `multi_tile_receipt`, receipt checksum OK | `2` |
| **Gamma** | `all_attested` — from `multi_tile_receipt`, all tiles attested | `4` |

Larger tiles earn higher rewards, reflecting the greater proof-of-compute contribution:
- Gamma (8×4 tile array) → 4 tokens/job
- Euler (8×2 tile array) → 2 tokens/job
- Phi (1×1 single tile) → 1 token/job

### 2. Accumulator Counts Tokens

`tri_token_accumulator` is a saturating counter (`WIDTH=16`, max 65 535 tokens per session) clocked by the chip's main clock:

```
on posedge clk:
  if !rst_n:          token_balance <= 0
  else if attest_pulse && !overflow_flag:
                      token_balance <= token_balance + reward_amount
overflow_flag = &token_balance   // all bits set → saturated
```

Key properties:
- **No `*` operators** (R-SI-1 compliant) — addition and concatenation only
- **Reset-safe** — balance zeroed on `rst_n = 0`
- **Saturating** — stops at `2^WIDTH − 1`; `overflow_flag` asserted when full
- **Verilog-2005** — portable across all synthesis flows

### 3. Off-Chip Prover Reads Balance via Status Mode

The token balance is exposed through the existing `ui_in[4:2]` status-mode decode without adding new pins:

| `ui_in[4:2]` | Mode | `uo_out` | `uio_out` |
|---|---|---|---|
| `3'b000` / `3'b001` | Canonical anchor | `0x47` | `0xC0` |
| `3'b010` … `3'b110` | Existing tile status | (preserved) | (preserved) |
| **`3'b111`** | **$TRI token balance** | `token_balance[7:0]` | `token_balance[15:8]` |

The prover asserts `ui_in[4:2] = 3'b111` then reads both bytes to reconstruct the 16-bit balance.

### 4. ERC-20 $TRI Minted 1:1 on Settlement Layer

Once the prover has read the balance:

1. It generates a signed attestation (including chip ID, session nonce, balance).
2. The attestation is submitted to the `$TRI` settlement contract on-chain.
3. The contract mints ERC-20 `$TRI` tokens **1:1** to the chip operator's wallet.
4. The on-chip balance is reset (via `rst_n` pulse) to begin the next session.

This design keeps all cryptographic verification off-chip, minimising silicon area while maintaining trustless settlement guarantees.

## Integration

Per-chip integration into `tt-trinity-{phi,euler,gamma}` is tracked separately. Each tile's top-level (`tt_um_*.v`) must:

1. Instantiate `tri_token_accumulator` with the correct `reward_amount` (hardwired).
2. Connect the tile-specific `attest_pulse` source (see table above).
3. Mux `token_balance[7:0]` → `uo_out` and `token_balance[15:8]` → `uio_out` when `ui_in[4:2] == 3'b111`.
